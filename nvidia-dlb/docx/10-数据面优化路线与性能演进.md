# 第 10 章：数据面优化路线与性能演进

本章只讨论 DLB 数据面的当前实现、性能瓶颈和后续优化路线。文中的
提升数字分为两类：

- **已实现收益**：代表性高吞吐负载下已经观察到的相对变化；
- **目标收益**：基于当前阶段占比和减少的实际内存操作数估算，需在生产拓扑、
  真实路由分布和完整 MoE 计算重叠下重新验证。

## 1. 优化目标

DLB 的调度原则不变：每个源服务器只根据本地 demand 选择源 Rail，并保留
每条记录的真实目标 expert。数据面优化围绕四个指标展开：

1. 同一 hidden 尽量少复制；
2. 数据生产、Rail 传输、目标修复和 expert 落位尽量重叠；
3. 路由控制信息保持在 GPU，热路径不引入 CPU 同步点；
4. 通信占用的 SM、buffer 和 QP 数量可控，不挤压 expert GEMM。

## 2. 已实现的结构性改进

### 2.1 按目标 Rank 去重 hidden

一个 token 的 Top-K expert 可能分布在少数几个 Rank 上。DLB 现在将同一
`(token, destination_rank)` 的多个 expert 选择合并到一条 wire record：

```text
逻辑 expert routes = tokens × topk
wire records          = Σtoken(unique destination ranks)
```

[`count_moe_routes_kernel()`](../src/dlb_alltoall/dlb_moe_runtime.cu) 负责计数，
[`pack_moe_direct_kernel()`](../src/dlb_alltoall/dlb_moe_runtime.cu) 把同 Rank 的 expert ID、
Top-K slot 和 weight 收进同一个 header。hidden 只复制一次。

若 Top-8 路由平均只触及 3–4 个目标 Rank，dispatch hidden 数据量会下降约
`50%–62.5%`。该收益随 expert 在 Rank 上的聚集程度变化。

### 2.2 直接写入 symmetric Rail buffer

初始化阶段为本服务器的 Rail 构造 peer pointer table。producer 不再先写私有
staging buffer，而是直接 pack 到选定 Rail 的 symmetric send buffer：

```text
source GPU
  -> selected Rail symmetric send buffer
  -> Rail transport
```

这删除了一份 staging 容量和一次完整 D2D copy。对大 hidden 负载，单独
staging 阶段基本被消除，端到端收益通常为 `3%–10%`。

### 2.3 固定通信 CTA 和多 channel 输送

Rail group 会被连续切分到 `C = num_comm_sms / 2` 个 channel，每个 channel 拥有独立的
metadata、progress 和 credit。sender/receiver 分别使用 `C` 个固定 CTA，不随
服务器数和 group 数无界增长。

```text
num_comm_sms = 24
  -> 12 sender CTAs
  -> 12 receiver CTAs
```

默认 CTA 使用 640 threads，让 20 个 warp 协同搬运 record payload。相比少数 warp
串行处理全部 group，固定 channel 设计已使 Rail 阶段减少约 `85%–91%`，
完整 dispatch 减少约 `80%–86%`。更多 CTA 还能提高通信吞吐，但会与 expert
GEMM 争抢 SM，因此不能只按通信 microbenchmark 选参数。

### 2.4 分块 progress/credit 流水线

同一 channel 不等整个 group 传完才通知接收端，而是按 chunk 发布连续前缀：

```text
发布 metadata
  -> 传输 chunk N
  -> 发布 progress N
  -> receiver 修复已完成前缀
  -> 继续传输/修复后续 chunk
  -> 整个 descriptor repair 完成后返还 credit
```

不同 channel 可以乱序完成；同一 channel 只暴露连续完成前缀，因此接收端不会
读到中间空洞。credit 保护的是 descriptor 对应 slot 的跨 epoch 复用：receiver
完成整个 slice 后才允许 sender 在下一次 slot 生命周期覆盖它。当前还不是每个
chunk 独立返还容量的 receiver-owned ring。

### 2.5 Combine 按 Rank/token 局部归并

dispatch 保留 `group_output_indices`。combine 在当前 expert Rank 上先将同一 group 的
expert output 按 router weight 做 FP32 局部求和，然后每个
`(source_rank, source_token, current_rank)` 只返回一条 record。

因此 combine wire records 同样与 token 命中的唯一 Rank 数成正比，而不是与
Top-K expert 数成正比。对与上述相同的 Top-8 路由分布，返程 hidden 传输量也可
下降约 `50%–62.5%`。

### 2.6 可选的 GPU 阶段监控

`DLBBuffer(enable_profiling=True)` 会记录 prepare、producer publish、Rail transport、
receive repair、count readback 和 materialize/accumulate 等边界。profiling 默认关闭，避免
为生产热路径引入 event 开销。

性能报告必须同时给出：

- logical expert routes；
- rank-deduplicated wire records；
- wire bytes 和 wire GB/s；
- Rail 总量与 channel 分布；
- 各阶段 P50/P95；
- 通信与 expert GEMM 重叠后的完整层时间。

## 3. 当前主要瓶颈

多 channel 已经解决了最突出的串行搬运问题，但当前 dispatch 仍是多段 kernel：

```text
route count
  -> local demand collect
  -> DLB plan
  -> direct pack
  -> transport
  -> repair buffer
  -> expert count
  -> host readback/synchronize
  -> allocate output
  -> expert scatter
```

其中最有价值的后续工作不是继续盲目增加 channel，而是减少中间 buffer、全局内存
往返和 host 参与。

## 4. 下一阶段优化路线

### 4.1 融合路由布局生成

用一个 GPU kernel 同时生成：

- per-expert 逻辑记录数；
- token-to-rank 去重 bitmap；
- per-rank/per-server demand；
- per-channel count 和 prefix；
- invalid expert 计数。

计数先在 warp/shared memory 局部归并，再写入全局数组，避免 Top-K 热点直接争用
global atomics。目标是使 prepare 阶段减少 `20%–50%`，完整 dispatch 减少约
`3%–10%`。

### 4.2 receiver-owned 环形队列

将当前“完整 transport slot + 完整 repair buffer”改为每个 `(channel, source)` 独立的
receiver-owned ring：

- sender 只推进 tail；
- receiver 只推进 head；
- sender 按可用 credit 写入 chunk；
- receiver 收到连续前缀后立即落位，无需等待整轮完成。

这会让 pack、Rail transport 和 destination repair 真正重叠，同时缩小峰值 buffer。目标
是完整 dispatch 减少 `15%–30%`，在 group 尺寸不均匀时收益可能更高。

### 4.3 融合 receive repair 与 expert materialization

当前接收端先把 record 复制到 repair buffer，再计数、分配和 scatter 到 expert rows。
生产路径应让 receiver 直接将完成 record 落到最终 grouped-GEMM 输入，或保留
token-per-rank payload 并用 expert-index mapping 供 GEMM 消费。

如果 grouped GEMM 可以直接消费去重布局，不仅能删除一次完整 record 读写，还能避免
在同 Rank 的多个 expert 之间重复展开 hidden。预期 receive/materialize 阶段提升
`1.5–2.5×`，完整 dispatch 减少 `10%–25%`。

### 4.4 TMA 与 shared-memory 分级搬运

对连续 hidden payload 使用对齐的大粒度异步 copy，通过 shared-memory stage 和 mbarrier
让一组 warp 预取下一个 record，另一组 warp 处理当前 record 的 metadata/落位。

这一优化只针对 payload-dominated 阶段，不能代替路由和同步优化。目标是使连续搬运
阶段提升 `1.5–2.5×`，对完整 dispatch 的贡献约为 `10%–30%`，具体取决于
hidden 宽度和中间 copy 是否已被融合。

### 4.5 去除 host readback 和强制同步

当前 binding 在接收后将 expert counts、Rail counts、channel counts、group count 和 invalid
count 拷回 CPU，并在分配输出前同步 stream。可选方案是：

1. 使用预分配的 bounded output，GPU 只写实际 count；
2. 把 count tensor 作为异步 handle 一部分交给下游；
3. 在 CUDA Graph 内固定容量，对超限路由返回设备端错误。

目标是消除 `0.05–0.15 ms` 的 CPU 往返/同步窗口，完整 dispatch 减少约
`3%–8%`，更重要的是恢复与其他 CUDA stream 的异步重叠。

### 4.6 融合 combine 接收、累加和 cast

当前 combine 先收到 repair records，再分配 FP32 中间 tensor，最后单独累加和 cast。
后续可以让 receiver warp 直接对 source token 做 FP32 累加，并在连续前缀完成后写出
最终 dtype。目标是 combine 端到端减少 `10%–25%`。

### 4.7 cached layout 与 CUDA Graph 快路径

对 topology、capacity、expert placement 和 tensor shape 不变的连续迭代，缓存：

- server/rail/expert 映射；
- buffer offsets 和 channel 容量；
- kernel launch 参数与 graph executable；
- 路由完全重复时的 prefix/layout handle。

动态 routing 仍需重算 demand 和 prefix，不能误用旧 plan。对形状稳定但路由变化的负载，
预期端到端收益为 `2%–5%`；对路由也稳定的重复执行，可达 `5%–15%`。

### 4.8 分层 credit 和连续完成窗口

当 channel 或 QP 数量增加后，物理 completion 可能乱序返回。数据面应使用一个
sliding completion window 记录已完成 chunk，只把最大连续前缀发布给 receiver；同时将
head/credit 更新批量化，减少远端 atomic/signal。

这对小 chunk、多 QP 和大规模拓扑更有价值。目标是 Rail 阶段减少 `10%–25%`，
但必须先保证跨 channel 乱序不会改变同 channel 的可见性语义。

### 4.9 专用 device-initiated transport 路径

当底层环境可用时，可增加 GPU 直接提交 WQE、推进 doorbell 和管理 completion 的
专用后端，减少 generic NVSHMEM RMA/signal 在小块和高并发下的额外开销。这个后端必须与
现有通用后端共享完全相同的 DLB plan 和 record 语义。

在真实 RDMA 环境完成验证前，这里不给出端到端承诺；对小到中等消息，可将
transport 阶段 `1.3–2×` 作为验证目标。

### 4.10 FP8 payload 和 metadata 紧凑化

BF16 hidden 每元素 2 bytes，FP8 payload 可把 hidden wire bytes 减少近一半，但需要携带
scale 并与 expert kernel 的量化协议一致。对通信受限的 dispatch，目标提升为
`1.4–1.8×`；对计算受限负载收益会更小。

当前 wire header 为 128 bytes。将固定控制字段与可变选择列表分开，并按实际 Top-K
编码，可将 header 收紧到约 32–64 bytes。hidden=2048 时端到端收益通常只有
`1%–3%`，但在小 hidden 或高 Top-K 下更有价值。

### 4.11 自适应通信资源

`num_comm_sms`、chunk bytes、ring depth 和每 channel QP 数不应永久固定。初始化时可根据
GPU SM 数、server/GPU 拓扑、hidden bytes 和最大在途 records 给出分析值，再用少量线上
profile 做分档选择。

目标是相比一套静态参数获得 `5%–20%` 的端到端收益，同时通过 SM 上限保护
expert GEMM 的 MFU。

### 4.12 超时、错误和可观测性

所有 device polling 都应有可配置的 cycle timeout，超时时写出 epoch、rank、channel、source、
destination、head/tail/progress 和 backend 状态，再终止当前操作。这不直接提高吞吐，
但是环形队列和多 QP 进入生产前的必要条件，可避免错误被表现为无限期 GPU hang。

## 5. 优先级与预期收益

| 优先级 | 改进 | 主要解决的问题 | 保守目标 |
|---:|---|---|---:|
| P0 | receiver-owned ring + 融合 repair/materialize | 中间 buffer 和串行阶段 | dispatch `-20%–40%` |
| P0 | 去除 host readback/sync | CPU 同步点、无法 graph capture | dispatch `-3%–8%` |
| P0 | device polling timeout | hang 不可诊断 | 可靠性改进 |
| P1 | TMA 分级搬运 | payload copy 效率 | copy `1.5–2.5×` |
| P1 | 融合路由布局 | 多 kernel、global atomic | prepare `-20%–50%` |
| P1 | 融合 combine 累加 | repair + FP32 中间张量 + cast | combine `-10%–25%` |
| P1 | cached layout/CUDA Graph | 重复 launch 和静态元数据 | end-to-end `-2%–15%` |
| P2 | 批量 credit + completion window | signal/atomic 频率和乱序完成 | Rail `-10%–25%` |
| P2 | device-initiated transport | 通用 transport 额外开销 | transport `1.3–2×` 目标 |
| P2 | FP8 payload | wire bytes | 通信受限路径 `1.4–1.8×` |
| P2 | 自适应资源 | 静态参数无法适配所有负载 | end-to-end `5%–20%` |

各项收益不能简单相加。例如融合 repair 后，TMA 可优化的独立 copy 时间会变小；
启用 FP8 后，路由和同步占比反而会升高。每一轮应只引入一个可归因的变量，并同时
验证正确性、P50/P95、wire bytes、Rail/channel 均衡和整层 MoE 重叠效果。

## 6. 目标数据面

```text
fused route layout
  -> producer 直接写 channel ring
  -> channel/QP 分块传输
  -> receiver 增量落位到 grouped-GEMM layout
  -> expert compute
  -> receiver-side FP32 local combine
  -> channel ring 返程
  -> source 端融合累加与 cast
```

这一路径不改变 DLB 的 source-local Rail 调度算法，只是将调度结果变成可持续流水化
消费的 GPU 数据面，并把 CPU 从每轮 dispatch/combine 的热路径中移出。
