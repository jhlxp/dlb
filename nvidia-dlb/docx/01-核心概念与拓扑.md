# 第 01 章：核心概念与生产拓扑

本章定义 rank、server、Rail、record 和 flow 的对象关系，以及它们在调度状态中的索引方式。

## 1. Rank 如何映射为物理服务器和本地 Rail

生产构造函数使用：

```cpp
server = rank / rails;
local_rank = rank % rails;
```

对应关系为：

```text
server_rank = global_rank / M
local_rank  = global_rank % M
```

在四服务器、单层 EP32 的生产场景中，`S=4`、`M=8`：

| 物理服务器 | global ranks | local rank/Rail |
| ---: | --- | --- |
| 0 | `0..7` | `0..7` |
| 1 | `8..15` | `0..7` |
| 2 | `16..23` | `0..7` |
| 3 | `24..31` | `0..7` |

匹配 Rail 是：

```text
Rail 0: rank 0  <-> rank 8  <-> rank 16 <-> rank 24
Rail 1: rank 1  <-> rank 9  <-> rank 17 <-> rank 25
...
Rail 7: rank 7  <-> rank 15 <-> rank 23 <-> rank 31
```

该拓扑中，每个 server 对应一台物理服务器。同号 Rail 通过各自的 NIC/网络平面连接其他服务器的同号 Rail。

## 2. 逻辑 route 与 dispatch wire record

一个逻辑 route 仍对应一个有效 `(token, topk_slot)`，包含六个身份：

```text
source_rank        record 最初属于哪个 EP Rank
source_token       该 Rank 输入 x 中的 token 下标
expert             router 选择的全局 expert
topk_slot          该 expert 是 token 的第几个 top-k 选择
destination_rank   expert 所属的真实 EP Rank
selected_rail      DLB 选择的物理出站 Rail
```

但 dispatch 不再为每个逻辑 route 重复发送 hidden。同一 token 发往同一
`destination_rank` 的一个或多个逻辑 routes 被合并成一条 wire record：

```text
epoch, source_rank, source_token, destination_rank
selection_count
experts[selection_count]
topk_slots[selection_count]
weights[selection_count]
hidden payload（仅一份）
```

`selected_rail` 不放在 record header 中。它由 record 位于哪个 Rail
buffer/transfer slice 隐式表达。接收端再按 `experts[]` 将 group record 展开成
公开的 expert rows。

若每个 Rank 有 `num_local_experts` 个专家：

```text
destination_rank = expert / num_local_experts
destination_server = destination_rank / M
destination_local_rank = destination_rank % M
```

## 3. EP32 的具体 group record 例子

假设：

```text
num_experts = 256
world_size = 32
num_local_experts = 8
source_rank = 3
source_token = 17
topk selections = [(slot 3, expert 165), (slot 6, expert 167)]
```

则：

```text
destination_rank = 165 / 8 = 167 / 8 = 20
destination_server = 20 / 8 = 2
destination_local_rank = 20 % 8 = 4
```

两个 expert 都部署在 server 2 的 rank 20，因此只发送一份 hidden，并在 header
中保存两个 `(expert, slot, weight)`。

若 DLB 选择 Rail 6：

```text
rank 3 -> rank 6 -> rank 22 -> rank 20
 source   src rail   dst rail   real dst
```

需要 source staging 和 destination repair。

若 DLB 选择 Rail 4：

```text
rank 3 -> rank 4 -> rank 20
```

数据到达 destination Rail 后已位于真实目标 GPU，无需 destination-side repair。`direct_priority` 优先选择 `selected_rail == destination_local_rank`。

## 4. flow、record、slice 和 slot

```text
flow
  一个 source local GPU 到一个 real destination local GPU 的逻辑记录集合

record
  dispatch 中的一个 token/destination-rank group；拥有固定大小 transport ABI

slice
  相同 remote server、selected Rail、real destination 的连续 records

slot
  可跨 epoch 复用的一段固定容量 buffer；由 credit/epoch 保护
```

DLB 按 group record 数均衡，不为每条 record 单独执行 NVSHMEM put。
`pack_moe_direct_kernel()` 先把 records 放成连续 slice，随后一个
`DlbRailTransfer` 分块传输整段 bytes。

当前 record 是固定大小，因此均衡 record 数等价于均衡 payload bytes。如果未来不同 token 使用不同 payload 大小，planner 必须改为按 bytes/权重均衡。

本文使用 `wire record` 指采用 transport ABI 的 grouped record；它不等于“必然经过
RNIC 的 record”。目标在本 Rank 或本服务器时，同一种 record 会直接写入本地/机内
repair buffer。只有跨服务器子集才形成真实 RDMA wire bytes。

## 5. 本服务器 demand 矩阵

每个 source GPU 首先统计一行：

```text
symmetric_demand_row[destination_rank]
```

本服务器 `M` 个 Rank 通过 `nvshmemx_uint64_fcollect_on_stream()` 收集为：

```text
symmetric_demand_matrix: M × (S*M)

行：source local GPU p
列：全局 destination rank
值：该 source GPU 发往该 destination rank 的 rank-deduplicated group record 数
```

DLB 没有收集整个集群的 `world_size × world_size` 矩阵。每台服务器只收集自己的 `M` 行，这是“source-server-local”的准确含义。

处理某个远端服务器时，从它的 `M` 列抽出：

```text
tile: M × M

行：source local GPU p
列：real destination local GPU r
```

## 6. 调度状态的三个维度

一个 tile 包含输入需求、Rail 聚合负载和完整物理路径三类状态：

```text
input[p][r]
  原始业务需求：source GPU p -> real destination GPU r

assigned[q][r]
  调度后汇总：selected Rail q -> real destination GPU r

source_to_nic[p][q][r]
  完整路径：source GPU p -> selected Rail q -> real destination GPU r
```

GPU 生产路径将完整路径状态扁平化为：

```text
flow_rail_counts[remote][source][rail][destination_local]
```

索引函数是 [`flow_rail_index()`](../src/dlb_alltoall/dlb_moe_runtime.cu)。

## 7. 同服务器 flow 与远端 flow

`pack_moe_direct_kernel()` 首先判断：

```text
destination_server == source_server ?
```

- 是：直接写真实目标 GPU 的 CUDA-IPC repair buffer，不进入 Rail planner；
- 否：根据 `flow_rail_counts` 选择 Rail，写对应 Rail GPU 的 CUDA-IPC send buffer。

在四机 EP32 部署中，同服务器 flow 只走机内 NVLink/P2P；跨服务器 flow 才进入 DLB Rail planner 和 NVSHMEM/RDMA transport。

## 8. 跨 Rail 乱序与正确性

不同 Rail/QP 之间没有全局顺序，但 DLB 不依赖到达先后：

- 每个 transfer 有独立的 destination byte range；
- metadata signal 编码本轮 offset 和 bytes；
- progress signal 表示已有多少 bytes 可安全 repair；
- record header 保存 source token 和该目标 Rank 上的 top-k selections；
- combine 按 header 恢复，而不是按网络到达顺序恢复。

通信协议要求以下 happens-before 关系：

```text
payload 可见 -> progress 可见 -> repair 完成 -> credit 归还
```
