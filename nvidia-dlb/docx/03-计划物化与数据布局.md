# 第 03 章：GPU 调度状态、Record 与 Buffer 布局

本章解释 DLB 在一个 epoch 内如何把路由需求变成 GPU 可直接执行的数据面状态：

```text
GPU 本地规划
  -> flow_rail_counts + rail_transfers
  -> record 直接 pack 到最终 Rail/repair slot
```

## 1. 一个 epoch 的 GPU 数据面状态

```text
local_demand_row       本 rank 的 destination record 计数
local_demand_matrix    本服务器 M 个 rank 的计数矩阵
flow_rail_counts       每个逻辑 flow 分给各 Rail 的 record 数
destination_cursors    pack 时给 flow 内 record 分配 ordinal
rail_transfers         当前 epoch 的 Rail byte descriptors
DlbRailReceivePlan     初始化时构建的固定 arrival 身份表
```

[`dlb_nvshmem_binding.cpp`](../dlb_nvshmem_binding.cpp) 的 `prepare_moe_direct()` 在当前 CUDA stream 上启动生成前五类动态状态的 CUDA/NVSHMEM 操作。
[`dlb_rail_receive_plan.cc`](../src/dlb_alltoall/dlb_rail_receive_plan.cc) 只在 runtime 初始化时根据拓扑生成最后一类表：每个目标 Rail 固定等待所有 `(source_server, final_destination_local)`，本轮的 offset/bytes 再由 metadata 动态通知。

随后 `pack_moe_direct_kernel` 直接写入：

- 远端 flow：选中 Rail GPU 的 CUDA-IPC `rail_send_buffer`；
- 同服务器 flow：真实目标 GPU 的 CUDA-IPC `repair_buffer`。

因此，路由选择和 payload 写入在同一个 GPU 数据面中衔接：planner 决定每个 flow 的 Rail 配额，pack kernel 根据该配额把每条 record 写入其最终的 Rail 或 repair slot。

## 2. 一条 MoE record 的二进制布局

record ABI 由 [`dlb_moe_runtime.cu`](../src/dlb_alltoall/dlb_moe_runtime.cu) 的 pack/scatter/combine kernels 共同使用：

| Byte offset | 大小 | 字段 |
|---:|---:|---|
| 0 | 8 | `epoch` |
| 8 | 8 | `source_rank` |
| 16 | 8 | `source_token_index` |
| 24 | 8 | `destination_rank` |
| 32 | 4 | `selection_count` |
| 36 | 4 | 保留 |
| 40 | 32 | `experts[8]`，INT32 |
| 72 | 8 | `topk_slots[8]`，UINT8 |
| 80 | 32 | `weights[8]`，FP32 |
| 112 | 16 | padding |
| 128 | `hidden * element_size` | activation payload，仅一份 |

总 record 大小：

```text
record_bytes = align_up(128 + hidden * dtype_size, 16)
```

以生产配置中的 `hidden=7168` 为例，当前 DLB 使用 BF16 payload：

```text
128 + 7168 * 2 = 14464 bytes
```

固定大小 record 具有以下实现性质：

- record ordinal 可以直接乘 `record_bytes` 定位；
- DLB 均衡 rank-deduplicated record 数就等价于均衡 dispatch wire bytes；
- transfer 可以把同 group 的 records 合并成连续大块。

## 3. Buffer 容量如何估算

Python 入口 [`dlb.py`](../dlb.py) 中：

```text
slot_records = num_max_tokens_per_rank * num_topk
slot_bytes   = align_up(slot_records * record_bytes, 16)
```

每个 pipeline slot 至少要容纳一个 rank 的最坏展开量。Rail send capacity 还要覆盖一条 Rail 面向所有远端服务器的聚合空间：

```text
rail_send_capacity >= max(
    slot_bytes,
    (server_count - 1) * slot_bytes
)
```

该公式按最坏展开量预留容量，实际 epoch 的写入量由路由结果决定。

## 4. runtime 中的主要 Buffer

[`dlb_alltoall_nvshmem.h`](../src/include/dlb_alltoall/dlb_alltoall_nvshmem.h) 和 [`dlb_alltoall_nvshmem.cu`](../src/dlb_alltoall/dlb_alltoall_nvshmem.cu) 管理：

| Buffer | 内存类型 | 作用 |
|---|---|---|
| symmetric Rail send buffer | NVSHMEM symmetric memory + peer pointer table | 所有本机 producer 直接 pack；也是 Rail kernel 的合法 RMA 源地址 |
| receive data | NVSHMEM symmetric memory | matching destination Rail 的网络落点 |
| `repair_buffer` | 每个 GPU 的 CUDA allocation + IPC 指针表 | 最终 destination GPU 按 source rank 分区的 record 区 |
| metadata/progress/credit | NVSHMEM symmetric memory | transfer 发布、分块可见性、slot 复用协议 |
| stage/completion signals | CUDA IPC 可见的 system-scope counters | 同服务器不同 GPU 进程间的 epoch 协调 |

远端 NVSHMEM put 的源地址是 symmetric Rail send buffer，目标地址是远端
symmetric receive buffer。中间不再有 private staging 到 symmetric buffer 的
D2D copy。接收端随后将 record repair 到真实目标 GPU。

## 5. 远端 flow 的 pack 地址如何确定

对一条 route：

1. 对每个 token 找到各个唯一 `destination_rank`，同 Rank 的 expert selections 合并。
2. 根据 `flow_rail_counts` 和该 flow 的 atomic ordinal，判断 group record 属于哪条 selected Rail。
3. 对该 Rail 上更早的 `(source, destination)` group 求前缀。
4. 写到：

```text
rail_send_table[selected_rail]
  + pipeline_slot_offset
  + remote_server_group_offset
  + destination_group_offset
  + record_ordinal * record_bytes
```

当前 dispatch launch 为每个 token 建一个 CUDA block。block 内遍历 Top-K，对该 token
的每个唯一目标 Rank 写一条 group record，同 Rank 的后续选择只并入 header。block 使用 128
threads 协作复制 payload，并优先用 `uint4` 做 16-byte 向量搬运。写完 record 后
执行 system-scope fence，确保另一个 GPU 进程看到 stage signal 前 payload 已可见。

## 6. 同服务器 flow 的 P2P 路径

如果 source 与 destination 属于同一台物理服务器，算法不做跨 Rail 均衡，也不进入 NVSHMEM 网络 transfer：

```text
source GPU
  -> pack_moe_direct
  -> destination GPU repair_buffer[source_rank partition]
```

这是 CUDA IPC/P2P 直接写。它与跨服务器 records 最终汇合到相同 repair buffer 格式，因此后续 count/scatter 不需要区分数据来自本机还是远端。

## 7. repair buffer 的分区

目标 GPU 的每个 pipeline slot 再按 `source_rank` 分区：

```text
repair_base
  + slot * world_size * repair_slot_bytes
  + source_rank * repair_slot_bytes
  + record_offset
```

这样不同 source rank 不会覆盖彼此。到齐后，接收侧遍历所有 source partitions，按 header 验证 epoch/destination，再统计和 scatter。

## 8. 固定拓扑表与动态 metadata

设 `C = num_comm_sms / 2`，接收端固定知道会有：

```text
(S - 1) * M * C
```

个远端 arrival 身份，对应 `(source_server, final_destination_local, channel)`；
但不知道某轮每个 arrival 有多少 bytes、落在 receive buffer 哪个 offset。

发送端把本轮信息编码为：

```text
metadata = ((slot_offset + 1) << 32) | (bytes + 1)
```

两个 `+1` 用于区分“尚未发布的零值”和合法的 offset 0 / bytes 0。零流量 transfer 仍发布有效 metadata，使接收端完成该 arrival 的协议状态转换。

当前协议把 offset 和 bytes 分别压入 metadata 的高、低 32 bit，因此每个 descriptor
必须满足 `slot_offset + 1 <= UINT32_MAX` 且 `bytes + 1 <= UINT32_MAX`。runtime 初始化
会拒绝 `receive_slot_bytes >= UINT32_MAX`；结合 planner 保证每个 slice 的 offset/bytes
不超过一个 receive slot，这个容量检查保护了 metadata 的 32-bit 编码范围。

## 9. 数据布局的最终目标

该布局将稀疏 token routes 转换为连续的传输和接收数据：

```text
稀疏 token routes
  -> 按目标 Rank 去重的固定大小 records
  -> 按 Rail/真实目标聚合的连续 bytes
  -> 少量大块 NVSHMEM transfers
  -> 目标 GPU 上按 local expert 连续排列
```

第 04 章说明 runtime 如何通过 stream、event、signal、progress、credit 和 epoch 组织这些 buffer。
