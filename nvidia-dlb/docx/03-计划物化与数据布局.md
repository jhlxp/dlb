# 第 03 章：GPU 调度状态、Record 与 Buffer 布局

```text
GPU 本地规划
  -> flow_rail_counts + device_transfers
  -> record 直接 pack 到最终 Rail/repair slot
```

## 1. 一个 epoch 的 GPU 数据面状态

```text
symmetric_demand_row       本 rank 的 destination record 计数
symmetric_demand_matrix    本服务器 M 个 rank 的计数矩阵
flow_rail_counts           每个 flow 分给各 Rail 的 record 数
destination_cursors        pack 时分配 record ordinal
device_transfers           当前 epoch 的 Rail byte descriptors
DlbRailReceivePlan         初始化时构建的固定 arrival 身份表
```

`prepare_moe_direct()` 生成前五项。`DlbRailReceivePlan` 在 runtime 初始化时根据拓扑生成。

`pack_moe_direct_kernel` 直接写入：

- 远端 flow：选中 Rail GPU 的 `symmetric_rail_send_buffer`；
- 同服务器 flow：目标 GPU 的 `local_repair_buffer`。

## 2. 一条 MoE record 的二进制布局

| Byte offset | 大小 | 字段 |
|---:|---:|---|
| 0 | 8 | `epoch` |
| 8 | 8 | `source_rank` |
| 16 | 8 | `source_token` |
| 24 | 8 | `destination_rank` |
| 32 | 4 | `selection_count` |
| 36 | 4 | 保留 |
| 40 | 32 | `experts[8]`，INT32 |
| 72 | 8 | `topk_slots[8]`，UINT8 |
| 80 | 32 | `weights[8]`，FP32 |
| 112 | 16 | padding |
| 128 | `hidden * element_size` | activation payload，仅一份 |

```text
record_bytes = align_up(128 + hidden * dtype_size, 16)
```

同一 token 发往同一 destination rank 的多个 expert selection 共用一份 payload，
expert、Top-K 位置和权重写入同一个 header。

## 3. Buffer 容量如何估算

```text
slot_records = num_max_tokens_per_rank * num_topk
slot_bytes   = align_up(slot_records * record_bytes, 16)
```

```text
rail_send_capacity = max(
    slot_bytes,
    (server_count - 1) * slot_bytes
)
```

```text
slot = epoch % pipeline_depth
```

`slot_bytes` 是一个 source-rank record 分区的容量，不是完整的 pipeline slot。
实际 record 数因 destination-rank 去重而不超过该容量。
默认 `pipeline_depth=2`。当前只允许一个 pending dispatch；两个 slot 隔离相邻
epoch 的 Buffer 和协议状态。

## 4. runtime 中的主要 Buffer

| 源码字段 | 内存类型 | 当前作用 |
|---|---|---|
| `symmetric_rail_send_buffer` | NVSHMEM symmetric memory + peer pointer table | 本机 source GPU 直接 pack 到选中的 Rail GPU；Rail transport 从这里读取 |
| `symmetric_receive_buffer` | NVSHMEM symmetric memory | 远端 `putmem_signal` 的目标，按 Buffer 分区和 source server 分区 |
| `local_repair_buffer` | CUDA allocation + IPC pointer table | 最终 destination GPU 的 record 区；每个 Buffer 分区内再按 source rank 分区 |
| `symmetric_receive_signals` | NVSHMEM symmetric memory | 发布每个 arrival 的 receive offset 和 byte count |
| `symmetric_progress_signals` | NVSHMEM symmetric memory | 发布每个 arrival 已连续到达的字节数 |
| `symmetric_credits` | NVSHMEM symmetric memory | 接收端消费完成后允许发送端复用协议位置 |
| `local_stage_signals` | CUDA IPC 可见的 system-scope counter | 本服务器各 producer 发布 pack/stage 已完成 |
| `local_completion_signals` | CUDA IPC 可见的 system-scope counter | 本服务器各 Rail 发布 receive/repair 已完成 |

远端传输使用 `nvshmemx_putmem_signal_warp`，没有额外的 private-to-symmetric D2D copy。

## 5. 远端 flow 的 pack 地址如何确定

1. 对每个 token 找到各个唯一 `destination_rank`，同 Rank 的 expert selections 合并。
2. 用 `destination_cursors` 原子分配 ordinal。
3. 根据 `flow_rail_counts` 选择 Rail，计算 `group_prefix` 和 `selected_ordinal`。
4. 写入：

```text
rail_send_tables[slot].device_ptrs[selected_rail]
  + remote_index * rail_slot_bytes
  + (group_prefix + selected_ordinal) * record_bytes
```

`rail_send_tables[slot]` 已指向当前 slot。kernel 为每个 token 启动一个 128-thread
block；payload 使用 TMA 或 `uint4`/字节复制。

## 6. 同服务器 flow 的 P2P 路径

如果 `source_server == destination_server`，算法不做跨 Rail 均衡，也不进入 NVSHMEM 网络 transfer：

```text
source GPU
  -> pack_moe_direct
  -> destination GPU local_repair_buffer[source_rank partition]
```

这是 CUDA IPC/P2P 直接写。远端 records 经 receive/repair 后进入相同布局。

## 7. repair buffer 的分区

目标 GPU 的 `local_repair_buffer` 先按 `slot` 分区，再按
`source_rank` 分区：

```text
repair_base
  + slot * world_size * repair_slot_bytes
  + source_rank * repair_slot_bytes
  + record_offset
```

接收侧按 header 验证 epoch/destination，再统计和 scatter。

## 8. 固定拓扑表与动态 metadata

设 `C = num_comm_sms / 2`，接收端固定知道会有：

```text
(S - 1) * M * C
```

个远端 arrival，对应 `(source_server, final_destination_local, channel)`。

```text
metadata = ((slot_offset + 1) << 32) | (bytes + 1)
```

`+1` 区分未发布的零值与合法的 offset/bytes 0。高低 32 bit 分别保存 offset 和
bytes；runtime 要求 `receive_slot_bytes < UINT32_MAX`。
