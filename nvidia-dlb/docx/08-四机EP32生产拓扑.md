# 第 08 章：四机 EP32 生产拓扑

本章使用四服务器、EP32、256 routed experts 的单层 MoE 通信场景，所有 server 都对应真实物理服务器。

```text
physical servers   = 4
GPUs/server        = 8
Rail NICs/server   = 8
EP world size      = 32
routed experts     = 256
experts/rank       = 8
topk               = 8
hidden             = 7168
payload dtype      = BF16
```

本章仅覆盖 256 个 routed experts；共享专家不参与 EP dispatch/combine 和 DLB 路由。

## 1. 物理服务器、Rank 与 Rail

```text
Server 0: ranks  0..7,  local Rails 0..7
Server 1: ranks  8..15, local Rails 0..7
Server 2: ranks 16..23, local Rails 0..7
Server 3: ranks 24..31, local Rails 0..7
```

对任意 global rank：

```text
server     = rank / 8
local_rail = rank % 8
```

同号 Rail 构成一个跨服务器网络平面：

```text
Rail q: rank q <-> rank (8+q) <-> rank (16+q) <-> rank (24+q)
```

它表示同号 NIC/Rail 之间的 scale-out 通路，不是说业务只能在同号 GPU 之间通信。真实目标 GPU 由 expert 归属决定。

## 2. 一层 MoE 如何展开为 Records

假设该 EP group 在当前层处理：

```text
global batch    = 16
sequence length = 2048
global tokens   = 32768
tokens/rank     = 1024（假设均匀分片）
```

每个 token 选择 8 个 routed experts，因此逻辑 expert routes 为：

```text
expert routes/rank = 1024 × 8 = 8192
global expert routes/layer = 32768 × 8 = 262144
```

dispatch wire 按目标 Rank 去重。若 `U(token)` 是该 token 的 8 个 expert 分布到
的唯一 Rank 数，则实际 wire records 为 `sum(U(token))`，上界仍为 8192/Rank。
当前 BF16 record 包含 128-byte grouped header 和 7168 个 BF16 hidden 元素：

```text
record_bytes = 128 + 7168 × 2 = 14464 bytes
wire bytes/rank = sum(U(token)) × 14464
worst-case wire bytes/rank = 8192 × 14464 = 113.0 MiB
```

这是进入 dispatch 热路径的 grouped-record 数据量上界，不等于全部经过 RNIC 的
wire bytes。其中有多少留在本 Rank、走机内 NVLink/P2P 或走跨机 RDMA，由本轮
router 结果决定；NIC 利用率只能用跨服务器子集计算。

## 3. 同服务器与跨服务器路径

如果 source rank 3 的 token 选中 server 0 上的 expert，`pack_moe_direct_kernel` 直接通过 CUDA IPC/P2P 写真实目标 GPU 的 repair buffer：

```text
rank 3 -> server 0 内的真实 destination rank
```

它不进入远端 tile，也不占用 scale-out Rail。

如果 expert 165 被 rank 3 上的 token 选中：

```text
experts/rank          = 8
destination_rank      = 165 / 8 = 20
destination_server    = 20 / 8 = 2
destination_local_gpu = 20 % 8 = 4
```

若 DLB 为该 record 选择 Rail 6，真实物理路径是：

```text
rank 3 producer
  -> server 0 内 direct pack 到 rank 6 / Rail 6 buffer
  -> Rail 6 RNIC/RDMA 发到 server 2 的 rank 22 / Rail 6
  -> server 2 内 repair 到真实目标 rank 20 / local GPU 4
```

选择 Rail 4 时，destination Rail 与真实目标 GPU 一致，无需 destination-side repair。

## 4. 每台源服务器独立调度

以 Server 0 为例，它只收集 ranks `0..7` 的 demand rows：

```text
local demand matrix = 8 × 32
```

对 Server 1、Server 2、Server 3 各切出一个 `8 × 8` tile。对每个 tile 单独计算：

```text
tile_total = N
base       = floor(N / 8)
remainder  = N % 8
```

该 source-server/destination-server 对上的八条 Rail 最终各获得 `base` 或 `base + 1` 条 records。Server 1/2/3 也同时使用各自的本地 demand 独立规划，不需要全集群 demand matrix。

## 5. 每个 Rail Rank 的 Transfer 规模

默认 `num_comm_sms=24`，因此 `C=12` 个 channel。生产 planner 为每个 Rail rank 生成：

```text
transfer_count = (server_count - 1) × rails_per_server × channels
               = (4 - 1) × 8 × 12
               = 288
```

这 288 个 descriptors 对应：

```text
3 个远端服务器 × 8 个真实 destination local GPUs × 12 个 channels
```

每个 descriptor 是一个 destination group 的 channel slice，聚合多条连续
records，不是一条 record 提交一次 RDMA。零流量 descriptor 仍用于推进
metadata/credit 协议。

## 6. 生产初始化

四台服务器上的 32 个进程依次建立：

1. PyTorch distributed EP32 process group。
2. 每个 rank 绑定一张 GPU。
3. EP group rank 0 生成并广播 NVSHMEM unique ID。
4. NVSHMEM world 初始化，并为每台服务器创建八 rank local team。
5. 同服务器 ranks 交换 CUDA IPC handles。
6. 分配 symmetric send/receive、metadata、progress 和 credit buffers。
7. 根据四机八 Rail 拓扑构建并上传固定的 `DlbRailReceivePlan` arrival-identity 表。

初始化完成后，业务层只保留一个 `DLBBuffer`，每层 MoE 依次调用 `post_dispatch()`、`ticket.finish()` 和 `combine()`。前两步是同一个 dispatch 数据面的提交与物化边界；没有独立的旧同步 dispatch backend。

## 7. 单层完整执行链

```text
hidden states [tokens/rank, 7168]
  -> router 生成 topk_idx/topk_weights
  -> DLB post/finish：EP32 路由扩展、Rail 均衡、RDMA 和 repair
  -> 每 rank 上 8 个 local experts 的 grouped GEMM/MLP
  -> DLB combine：结果返回 source rank
  -> 按 source token/top-k weight 做 FP32 累加
  -> 恢复 [tokens/rank, 7168]
```

下一层有自己的 router 结果，因此 DLB 每轮重新统计本层 demand 并生成 source-local Rail plan。

## 8. 生产部署必须校验的拓扑

- 每台服务器的 local rank 到 GPU/NIC Rail 映射一致；
- 同号 Rail 实际绑定到预期 RNIC/网络平面；
- GPU 到本地 Rail staging buffer 的 CUDA P2P/IPC 可达；
- NVSHMEM 已选中预期 IBRC/IBGDA transport；
- GPUDirect RDMA 注册、PCIe/NUMA 和 NIC affinity 符合部署拓扑；
- 四台服务器的 rank 生命周期一致，collective init/close 不会缺 rank。

`gpus_per_server=8` 是应用提供的逻辑拓扑配置，不是 DLB 对服务器或 Rail 的硬件自动发现。上述 rank/GPU/NIC 映射必须由 launcher、`CUDA_VISIBLE_DEVICES`、NIC affinity 和部署检查共同保证。

上述拓扑约束是生产正确性与性能的必要条件；floor/ceil 算法检查不能覆盖此类部署问题。
