# 第 02 章：源服务器本地调度算法

DLB 在每台源服务器独立处理本机需求。对每个远端服务器对应的 `M × M` tile，规划器将 records 均匀分配到本机 `M` 条 Rail，不收集全集群需求矩阵。

本章定义 DLB 的算法契约，并对应到 GPU 热路径中的 `build_dynamic_rail_plan_kernel()`。调度输入、状态和输出驻留在 GPU。

## 1. 调度输入

设：

```text
S = server_count
M = rails_per_server = 每台服务器的 GPU/NIC 数
world_size = S * M
```

一台源服务器持有 `M × world_size` 的需求矩阵：

```text
demand[source_local_gpu][destination_rank] = record 数
```

对某个远端服务器切出连续的 `M` 列，就得到一个 tile：

```text
tile[source_local_gpu][destination_local_gpu]
```

四机 EP32 生产拓扑中 `M=8`，每个服务器对应的 tile 是 `8 × 8`：

```text
             远端真实目标 local GPU
             0    1    2   ...   7
源 GPU 0    a00  a01  a02  ...  a07
源 GPU 1    a10  a11  a12  ...  a17
...
源 GPU 7    a70  a71  a72  ...  a77
```

每个单元可以代表很多 records。DLB 不改变 record 的真实目标，只选择它从本机哪条 Rail 发出。

## 2. 初始方案：每张 GPU 使用自己的 Rail

规划从默认映射开始：

```text
source GPU p -> selected source Rail p
             -> destination Rail p
             -> real destination GPU r
```

因此初始 Rail 负载就是 tile 每一行的和：

```text
source_load[p] = sum(tile[p][r])
```

若八行负载为 `[16, 8, 4, 4, 0, 0, 0, 0]`，直接发送就会让前两条 Rail 过载，后四条 Rail 完全闲置。

## 3. 计算严格均衡的目标

对一个 tile 的总量 `total`：

```text
base      = floor(total / M)
remainder = total % M
```

每条 Rail 分配 `base` 条 record，另有 `remainder` 条 Rail 各增加一条 record：

```text
max(rail_load) - min(rail_load) <= 1 record
```

余数起点不是永远为 Rail 0，源码使用：

```text
(source_server * 17 + destination_server * 31 + round_id) % M
```

轮换多出来的 records，避免长期让固定 Rail 承担余数。

例子：

```text
初始负载 = [16, 8, 4, 4, 0, 0, 0, 0]
total    = 32
目标负载 = [4, 4, 4, 4, 4, 4, 4, 4]
surplus  = [12, 4, 0, 0, 0, 0, 0, 0]
deficit  = [0, 0, 0, 0, 4, 4, 4, 4]
```

source GPU 0 和 1 的 surplus records 被分配至 Rail 4–7；该 server-pair 的八条 Rail 最终各承载 4 条 record。

## 4. records 如何从 surplus 搬到 deficit

规划器维护每个 `(source GPU, selected Rail, real destination GPU)` 三元组的 record 数：

```text
assigned[selected_rail][real_destination]
source_to_nic[source_gpu][selected_rail][real_destination]
```

`source_to_nic` 保留 source GPU、selected Rail 与真实 destination GPU 三者的对应关系；Rail 重分配不改变 source 和 destination 身份。

一次迁移量是：

```text
moved = min(
    source p 剩余 surplus,
    rail q 剩余 deficit,
    flow p->r 当前还有多少 record
)
```

随后更新：

```text
source_to_nic[p][p][r] -= moved
source_to_nic[p][q][r] += moved
```

物理路径由此变成：

```text
source GPU p
  -- 本机 CUDA IPC/NVLink staging --> source Rail q
  -- NVSHMEM --> destination Rail q
  -- 必要时 repair --> real destination GPU r
```

## 5. `direct_priority`：均衡相同时少做 repair

为 deficit Rail `q` 挑记录时，算法优先挑 `real_destination == q` 的 flow：

```text
source GPU p -> source Rail q -> destination Rail q
                               == real destination GPU q
```

这种 record 到远端后已经处于最终 GPU，不需要目标侧转发。

当 `real_destination == q` 的 records 数量不足时，规划器选择 `r != q` 的 records。该分配保持路由正确性，但到达 destination Rail `q` 后需通过 CUDA IPC/NVLink 写入真实目标 GPU `r`。

所以 DLB 的目标优先级是：

1. Rail record 数严格均衡。
2. 在满足均衡的方案中，尽量减少目标侧 repair。

它不是一个全局最小转发量优化器。

## 6. 调度正确性契约

每个 tile 的结果必须同时满足：

- tile 总 record 数守恒；
- 每个真实目标 GPU 的列和守恒；
- 每个 source GPU 发出的 flow 总数守恒；
- selected Rail 的负载等于目标值；
- 任意两条 Rail 的负载差不超过 1；
- staging、direct、repair 的统计与实际分配一致。

有效调度结果必须同时保持 record 总数、source flow 总数和真实 destination 不变。

## 7. GPU 生产实现

生产入口是 [`launch_dlb_build_dynamic_rail_plan()`](../src/dlb_alltoall/dlb_moe_runtime.cu)。调用链是：

```text
topk_idx
  -> count_moe_routes_kernel
  -> NVSHMEM local-team fcollect
  -> build_dynamic_rail_plan_kernel
```

### 7.1 路由计数

`count_moe_routes_kernel` 用一个线程检查一个 `(token, topk_slot)`，但只在该
slot 是 token 对某个目标 Rank 的第一次命中时计数：

```text
destination_rank = expert_id / num_local_experts
if no earlier topk slot maps to destination_rank:
    atomicAdd(local_demand_row[destination_rank], 1)
```

所以一个 token 的 `topk=8` 仍表示 8 条逻辑 expert routes，但 dispatch demand
和 wire record 数等于它命中的唯一目标 Rank 数。越界 expert 只累加
`invalid_route_count`，不进入 demand。

### 7.2 只在源服务器内部收集需求

`nvshmemx_uint64_fcollect_on_stream(local_team, ...)` 把本机 `M` 张 GPU 的 demand row 收集成 `M × world_size` 矩阵。

该 collective 的作用域为本机 local team；不同源服务器不交换各自的源端需求，也不互相等待调度结果。

### 7.3 GPU 上构建 tile

GPU kernel 为每个远端服务器分配一个 block。当前实现只让 `threadIdx.x == 0` 执行该小规模整数规划；在 `M=8` 的生产拓扑中，每个 tile 也只有 64 个计数项，并行化这个小循环收益有限。

内部使用固定大小局部数组，并限制：

```text
M <= 8
```

它生成扁平表：

```text
flow_rail_counts[
  remote_server,
  source_local_gpu,
  selected_rail,
  real_destination_local_gpu
]
```

每张本机 GPU 都拥有同一 demand matrix，因此能独立算出完全一致的分配；但每个进程最终只物化属于自身 `local_rail` 的网络 transfer descriptors。

## 8. 每个 Rail 的 transfer descriptor 数量

一张 Rail GPU 对每个远端服务器、每个真实 destination local GPU 先聚合一个
连续 group，再将 group 切到 `C = num_comm_sms / 2` 个 channel：

```text
transfer_count_per_rank = (S - 1) * M * C
```

一个 transfer 表示一个 group 在某个 channel 上的连续 slice，可包含很多 records，
而不是一条 record 发一次 NVSHMEM put。`DlbRailTransfer` 的实际字段为：

```text
destination_rank = destination_server * M + local_rail
source_offset_bytes / destination_offset_bytes / bytes
signal_index / credit_index
channel_index
```

`final_destination` 不在动态 transfer descriptor 中。transfer 在数组里的固定顺序是
`(remote_server, destination_local, channel)`；目标 Rail 初始化时构建的
`DlbRailArrival` 用相同的 signal/channel 索引保存 `final_destination_rank`。网络传输
首先到达远端 matching Rail，接收端再依据 arrival 表执行 repair。

## 9. 从算法到 GPU 数据结构

| 算法概念 | GPU 表示 | 后续消费者 |
|---|---|---|
| `demand[p][r]` | `symmetric_demand_matrix` | Rail planner |
| `source_to_rail[p][q][r]` | `flow_rail_counts[remote][p][q][r]` | direct pack |
| 每条 Rail 的负载 | `device_rail_record_counts[q]` | 可观测性与均衡检查 |
| `(remote server, final destination, channel)` 的连续分段 | `DlbRailTransfer` + 静态 `DlbRailArrival` | NVSHMEM Rail transport/repair |

算法规约位于 [`dlb_scheduler.cc`](../src/dlb_alltoall/dlb_scheduler.cc)，GPU 实现位于 [`dlb_moe_runtime.cu`](../src/dlb_alltoall/dlb_moe_runtime.cu)。两者共享相同的 floor/ceil 均衡、direct-priority 和 record 守恒规则。

## 10. 当前算法边界

- 均衡单位是固定大小 record 数；当前 MoE record 大小相同，因此也等价于均衡 bytes。
- `M` 当前最多为 8。
- 只处理远端服务器 tile；同服务器流量直接 P2P 到真实目标 GPU。
- 算法保证每个 tile 内 Rail 均衡，不承诺全局网络拥塞最优。
- 多 Rail 到达顺序不固定；正确性依赖 record header、epoch、计数与最终 scatter/combine，不依赖全局顺序。
