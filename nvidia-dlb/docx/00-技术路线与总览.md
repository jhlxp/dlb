# 第 00 章：架构总览与阅读地图

本文档以生产级 MoE dispatch/combine 的实际执行路径为主线：route 计数、服务器内需求收集、Rail 分配、数据打包、跨机传输、接收端修复和结果回传的 payload 数据面均由 GPU/NVSHMEM runtime 完成。当前精确输出 shape 仍有一次小型计数 D2H 同步，模型 router 与 expert 计算不属于 DLB。

## 1. DLB 定义

DLB 在每台源服务器内部独立统计本机 MoE 路由需求，把发往每个远端服务器的 records 尽量均匀地分配给本机 `M` 条 Rail；它只改变物理出站路径，不改变 token 选择的 expert 和真实目标 GPU。

设：

- `S`：物理服务器数量；
- `M`：每台服务器的 GPU/Rail 数量；
- `world_size = S * M`；
- `record`：dispatch 时一个 `(token, destination_rank)` group 对应的传输单元，可携带该 Rank 上的多个 Top-K 选择；
- Rail `q`：source server 的 local GPU `q` 到 destination server 的 local GPU `q` 的跨节点路径。

一条远端 record 的完整路径是：

```text
source GPU p
  -> selected source Rail q
  -> destination Rail q
  -> real destination GPU r
```

`q` 是 DLB 选择的物理路径，`r` 是 MoE router 决定的业务目标。`q` 可以变化，`r` 不能变化。

整套文档统一使用一个四服务器、EP32、256 routed experts 的单层 MoE 生产场景。

```text
physical servers   = 4
GPUs/Rails/server  = 8
EP world size      = 32
routed experts     = 256
experts/rank       = 8
topk               = 8
hidden             = 7168
```

共享专家属于本地计算路径，不纳入这 256 个 routed experts 或 EP all-to-all。

## 2. 生产执行路径

```text
模型 router
  -> DLBBuffer.dispatch()
  -> C++ dlb_nvshmem_comm_t::dispatch_moe()
  -> count_moe_routes_kernel
  -> server-local NVSHMEM fcollect
  -> build_dynamic_rail_plan_kernel
  -> pack_moe_direct_kernel
  -> launch_dlb_nvshmem_rdma
  -> count_received_experts_kernel
  -> scatter_received_experts_kernel
  -> expert-grouped recv_x + DLBHandle
```

这条路径把 route count、服务器内 demand 收集、DLB 规划和 record pack 留在 GPU 上。Python 不展开 records，也不构建 `M × (S*M)` Python 矩阵。

`dlb_scheduler.cc` 是调度规则的可执行规约，用于验证 record 守恒、每条 Rail 的 floor/ceil 均衡和 forwarding 分类。生产实现位于 `build_dynamic_rail_plan_kernel()`；两者共享相同的不变量。

## 3. 一次完整 MoE 前向

```text
x + topk_idx + topk_weights
        |
        v
dispatch：同一 token 发往同一目标 Rank 的 Top-K 选择合并为一条 wire record
        |
        v
DLB：选择 source Rail，完成同服务器直达或远端 Rail 传输
        |
        v
按本地 expert 分组并对齐的 recv_x
        |
        v
本地 grouped expert GEMM/MLP
        |
        v
combine：目标 Rank 内先聚合同一 source token 的 expert 输出，再按 source_rank/source_token 送回
        |
        v
FP32 累加各 top-k expert 输出，恢复原 token 顺序
```

DLB 不负责 router 和 expert 计算。它负责 dispatch/combine 的数据移动、物理 Rail 选择和恢复所需的 metadata。

## 4. 控制信息与数据面

| 内容 | 当前生产位置 | 作用 |
| --- | --- | --- |
| 每目标 Rank 的 route count | GPU `symmetric_demand_row` | 当前 source GPU 的逻辑需求 |
| 本服务器完整 demand | GPU `symmetric_demand_matrix` | `M × (S*M)` 本地调度输入 |
| 每 flow 的 Rail 分配 | GPU `device_flow_rail_counts` | `[remote][source][rail][dst_local]` |
| Rail transfer 描述符 | GPU `runtime.device_transfers` | source/destination offset、bytes、signal、credit |
| payload record | symmetric Rail buffer 或 CUDA-IPC repair buffer | 128-byte grouped dispatch header + hidden payload |
| 到达协议 | NVSHMEM metadata/progress/credit | 顺序、完成与槽位复用 |
