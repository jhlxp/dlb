# 第 09 章：测试、性能与生产边界

判断 DLB 是否可生产使用，需要分别验证：

```text
算法不变量
GPU 数据布局
跨 rank 同步协议
端到端 MoE 数值正确性
性能与容量
真实多机 transport
```

生产验收需要同时覆盖算法、数据布局、同步协议、数值正确性、容量和多机传输性能。

## 1. 测试目录的职责

[`tests/`](../tests) 中当前保留三类有效测试：

- [`test_dlb_scheduler.cc`](../tests/test_dlb_scheduler.cc)：验证 floor/ceil、record 守恒和 forwarding 统计。
- [`test_dlb_invalid_expert.py`](../tests/test_dlb_invalid_expert.py)：分布式注入越界 expert ID，验证 fail-fast 不导致 collective 死锁。
- [`test_dlb_moe_network.py`](../tests/test_dlb_moe_network.py)：构造确定性 router、dispatch、本地 expert MLP、combine，并与 oracle 对比。该端到端回归同时覆盖 pack、header、NVSHMEM epoch/signal/credit、repair、scatter/combine 和 ping-pong slot 复用。

运行脚本与工具放在 [`scripts/`](../scripts)，测试输出统一写入 [`log/`](../log)。

这些是开发回归，不定义生产拓扑或生产 workload。架构、容量和性能分析统一以下面的真实四机 EP32 场景为准。

## 2. 生产基准场景：四服务器 EP32 单层 MoE

```text
physical servers    = 4
world_size          = 32
GPUs/Rails/server   = 8
EP size             = 32
global batch        = 16
sequence length     = 2048
global tokens       = 32768
tokens per rank     = 1024（假设该 EP group 内均匀分片）
hidden              = 7168
dtype               = BF16
routed experts      = 256
local experts/rank  = 8
topk                = 8
expert alignment    = 128（应与下游 grouped GEMM tile 对齐）
```

这里只统计 routed experts；共享专家不参与 EP all-to-all。

每个 rank 的逻辑 expert routes：

```text
1024 × 8 = 8192 expert routes
```

每条 rank-deduplicated BF16 dispatch wire record 为：

```text
128 + 7168 × 2 = 14464 bytes
```

设 `U(token)` 为一个 token 命中的唯一目标 Rank 数，则单 Rank 实际处理：

```text
wire records = sum(U(token)) <= 8192
wire bytes   = sum(U(token)) × 14464
```

全层逻辑 expert routes 为 `262144`，但这不再等于实际 hidden 传输次数。性能
报告必须同时列出 expert routes、唯一目标 Rank wire records，以及其中本 Rank、
机内 NVLink 和跨机 RDMA 的 bytes。

## 3. 端到端正确性 oracle

生产验收使用固定 router 输出和完整专家权重参考，并比较：

```text
DLB dispatch
  -> 每个 rank 本地 expert MLP
  -> DLB combine
```

与单进程/逻辑 oracle：

```text
按 topk_idx 直接选择对应 expert
  -> 计算 expert 输出
  -> 乘 topk weight
  -> 按 token 求和
```

至少检查：

- 每个 source route 只出现一次；
- expert ID 和 destination rank 正确；
- combine 返回的 top-k weights 正确；
- 最终 activation 在合理数值容差内一致；
- 所有 ranks 正常跨 epoch 结束，无 signal/credit 死锁。

## 4. 负载均衡检查

对每个 `(source_server, destination_server)` tile：

```text
sum(rail_counts) == tile total
max(rail_counts) - min(rail_counts) <= 1
```

进一步分析均衡代价时，应由 GPU 侧 counters 分类：

```text
direct：source GPU == selected Rail 且 destination Rail == real destination
source-only staging：source GPU != selected Rail，但远端无需 repair
destination-only repair：source 不 staging，但远端需要 repair
two-sided forwarding：source staging 且 destination repair
```

当前 binding 将 GPU 上的 `device_rail_record_counts` 和 channel counters 复制为
pinned CPU tensors，并分别保存在 `DLBHandle.dispatch_rail_traffic_records` 与
`DLBHandle.dispatch_channel_traffic_records`。后者表示该 Rank 每个固定通信 channel 的 records。
测试必须同时验证 channel 总和等于本 Rank 的 Rail 总量。上述四类 forwarding
计数尚未全部从 GPU 热路径直接回传；这是生产可观测性缺口，应通过 GPU counters
补齐，而不是把 records 拉回 Python 分类。

## 5. 性能应该如何分段

route/plan/pack/scatter 位于 GPU 热路径。阶段开销应使用 CUDA events 或 Nsight Systems/Compute 测量：

```text
rank-deduplicated route count
local-team fcollect
GPU DLB planner
direct pack
NVSHMEM transport + receive/repair
expert count/scatter
combine group-local FP32 weighted sum + pack
combine transport
FP32 accumulate + cast
```

`DLBBuffer(enable_profiling=True)` 可以在不改变数据面语义的前提下记录两条
CUDA-event 时间线。dispatch 通过 `get_last_dispatch_profile()` 读取，combine
通过 `get_last_combine_profile()` 读取。生产默认关闭，避免 timed events 进入热路径。

同时单独报告 API 端到端 wall time，它包含 PyTorch allocation 和小计数 D2H 同步。

## 6. 生产性能报告必须包含什么

生产性能结论应基于四机 EP32 场景；在相同 router 输入下报告以下指标：

| 类别 | 必须报告的内容 |
|---|---|
| Workload | tokens、topk、records、record bytes、本地/机内/跨机 bytes |
| DLB 算法 | 每 server-pair tile total、8 Rail loads、max-min gap、planner time |
| Forwarding | direct、source-only、destination-only、two-sided records/bytes |
| GPU 热路径 | count、fcollect、plan、pack、scatter、combine 的 P50/P90/P99 |
| Scale-out | 每 Rail/NIC/channel bytes、有效 GB/s、线速利用率、tail latency |
| API | dispatch/combine 端到端时间、allocation/D2H 边界、显存峰值 |
| Correctness | route 守恒、expert 计数、max/mean error、多 epoch slot/credit 状态 |

单一 dispatch wall time 无法定位 planner、GPU copy、RNIC、交换机或 destination repair 的瓶颈。

## 7. 日志规范

每次完整实验创建：

```text
nvidia-dlb/log/YYYYMMDD-HHMMSS-xxxx/
```

当前脚本实际保存：

```text
command.txt       完整启动命令
environment.txt   host、Python、PyTorch、CUDA 和 GPU capability
stdout.log        所有 ranks 的合并标准输出/错误
result.json       workload、正确性、性能、显存以及 Rail/channel 统计
status.txt        pass/fail、退出码和结束时间
```

进一步做多机验收时，应增加各 Rank 独立日志、commit、每个 server-pair tile 的
traffic，以及可选的 Nsight 输出。当前合并 `stdout.log` 足以保存回归现场，但不足以
快速定位大规模作业中的单 Rank 异常。

## 8. 当前生产边界

### 8.1 算法与拓扑

- `rails_per_server <= 8`；
- `topk` 当前范围为 `1..8`；
- `num_comm_sms` 必须是正偶数且不超过当前 GPU 的 SM 数；
- 当前 Rail runtime 要求 `server_count >= 2`，生产部署中每个 server 对应一台物理服务器；
- experts 按 rank 等量、连续编号；
- 负载按固定 record 数均衡，不支持变长 payload cost model；
- source-local 均衡不保证全局交换机拥塞最优。

### 8.2 API 与执行

- dispatch 为精确输出 shape 存在小型计数 D2H + stream synchronize；
- `topk_idx` 越界由 GPU invalid counter 统计，并在 dispatch 的小型计数 D2H 边界 fail-fast；
- 当前 payload 支持 FP16/BF16/FP32，尚未接入 FP8 输入路径；
- 当前每轮仍执行 count/fcollect/plan，没有真正 layout-cache 快路径；
- 输出 expert 区间内顺序由 atomics 决定，不保证确定顺序；
- combine FP32 atomic 累加可能有末位非确定性；
- buffer 依赖初始化容量，当前不做热路径自动扩容。
- 零 token 输入和完全为空的本地 combine 批次尚未形成完整 fast path；生产调用
  当前应保证每个 Rank 有非空输入，并在接入稀疏/动态 batch 前补充空批次回归。
- metadata 将单 descriptor 的 receive offset 和 bytes 各编码为 32 bit，因此
  `receive_slot_bytes` 必须小于 `UINT32_MAX`；runtime 初始化会检查该容量边界。

### 8.3 性能

- direct pack 当前每个 source token 使用一个 block，在 block 内合并同目标 Rank 的 Top-K selections；
- Rail producer 已直接写 symmetric send buffer，不再有 staging D2D copy；
- Rail transport 使用固定 sender/receiver channel CTA；默认 `num_comm_sms=24`，吞吐优先配置可单独调大；
- 大量小 flow、极端稀疏 tile 和不同 chunk size 仍需系统 benchmark；
- 需在 hidden 7168、Top-8、256 experts 的实际四机 workload 上评估 SM 占用、显存带宽和 expert compute overlap。

### 8.4 多机可靠性

- 四台物理服务器上的 EP32 正确性和性能尚需完成硬件验收；
- 需验证 IBRC/IBGDA、NIC 绑定、Rail 物理隔离和交换机拥塞；
- 当前没有完整的 rank failure、超时恢复或弹性重配置协议；
- collective init/close 要求所有 ranks 生命周期一致。

## 9. 走向生产的验收顺序

1. 用随机 demand matrix 验证 record 守恒、真实目标守恒和每个 tile 的 floor/ceil Rail 均衡。
2. 四台物理服务器建立 EP32 communicator，验证 32 ranks 的 NVSHMEM init/close 和 Rail 物理映射。
3. 使用 hidden 7168、256 routed experts、Top-8 完成单层 dispatch→expert→combine 数值对比。
4. 连续多 epoch 压测 metadata/progress/credit、ping-pong slot 和 buffer 容量。
5. 分别验证 IBRC/IBGDA，报告每 NIC bytes、链路利用率和 tail latency。
6. 与其他 all-to-all 基线在相同 routing、dtype、batch、EP32 拓扑下对比。
7. 加入 rank/NIC 错误注入、超时诊断、日志与生产监控。

## 10. 阅读代码时的最终检查问题

每项优化应验证以下四项不变量：

```text
record 是否守恒？
真实 destination 是否保留？
payload 与 ready signal 是否有正确 happens-before？
pipeline slot 是否在 receiver 消费完前被复用？
```

这四项不变量用于评估 DLB 优化的正确性风险。
